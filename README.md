# 科研经费拨款核对（Flask + Docker Compose）

上传拨款表、归属表、归口表三份 CSV，按**拨款日**做两层内连接，核算各统计单位的
实际合计与实际入表次数，并列出漏计、多计的单号。

另设**补录来源行号**入口：为旧入仓明细补齐归属行号 / 归口行号——上传三份 CSV
与同一单号的入仓明细，按拨款日取符合明细已有字段的路径，人工确认 / 撤销后
整单重判，存在唯一完整配法时下载补齐结果的 CSV。

## 启动方式

### Docker Compose（交付方式）

```bash
docker compose up --build
# 浏览器打开 http://localhost:8000
```

容器以非 root 用户运行 gunicorn（2 worker × 4 线程），带健康检查。
停止：`docker compose down`。

### 无 Docker 时本地运行

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
gunicorn --bind 0.0.0.0:8000 app.web:app     # 或 flask --app app.web run
```

## 输入格式（UTF-8，首行表头，列顺序固定）

| 文件 | 列 |
|---|---|
| 拨款表 | `单号, 项目号, 拨款日, 金额_分` |
| 归属表 | `行号, 项目号, 学院码, 起日, 止日` |
| 归口表 | `行号, 学院码, 统计单位, 起日, 止日` |

- 日期 `YYYY-MM-DD`；有效期为 **[起日, 止日)**，含起日、不含止日。
- 金额单位为分、非负整数；单号与两表行号各自唯一（违反即整次退回）。
- 外键不存在（如项目号在归属表无任何行）不算输入错误，按漏计处理。

## 核对规则

一条完整匹配路径 = 一条拨款日有效的归属行 + 一条该归属学院下拨款日有效的归口行。

1. **第一层（归属层）**：`项目号` 相等且拨款日落入归属有效期。命中 0 行 →
   漏计，断在**归属层**。
2. **第二层（归口层）**：对每条命中归属行的`学院码`，找拨款日有效的归口行。
   全部学院都无有效归口 → 漏计，断在**归口层**（页面注明已命中几条归属）。
3. 完整路径数 = **实际入表次数**：0 为漏计，1 为正常，>1 为多计。
4. **同一统计单位的不同匹配路径分别计入**，金额按路径数倍乘。
5. 多计页面给出两条匹配路径示例，各自标出归属表行号与归口表行号，
   并按统计单位列出路径数分布。

### 为什么不枚举匹配路径也能算合计与次数

设某笔拨款在学院 c 命中 `n_attr(c)` 条归属行、该学院拨款日有 `n_jur(c)` 条归口行，
归口行 j 指向统计单位 u，则：

```
该归口行对应的路径数 = n_attr(c)
单位 u 的入表次数  += n_attr(c)
单位 u 的合计      += n_attr(c) × 金额
```

引擎按“学院 → 有效归口行”聚合，只做加法与乘法，**不构造归属×归口的笛卡尔积**。
时间复杂度只与命中的归属行、归口行数量有关，与路径总数（乘积）无关。
自测中 600 归属 × 800 归口 = 48 万条路径，引擎仅构造 2 个用于页面展示的
示例路径对象即完成全部合计与次数计算。

## 补录来源行号

首页点“进入补录入口”（或访问 `/backfill`），上传拨款表、归属表、归口表与
**同一单号**的入仓明细四份 CSV，进入该单的补录核对页。

入仓明细列：`入仓行号, 单号, 统计单位, 归属行号, 归口行号`（入仓行号唯一；
末两列缺项留空，已填则作为约束）。

### 规则

1. **取路径**：按单号的拨款日做两层内连接（与核对入口同一规则），每条明细的
   候选路径 = 符合其已有字段（统计单位必等；归属/归口行号已填则必等）的有效路径。
2. **一对一**：同一对（归属行号，归口行号）只能分给一条明细。
3. **状态**：每条明细区分为 人工已确认 / 可唯一推定（仅剩 1 条候选）/
   待核（多条候选）/ 无候选路径。
4. **确认与撤销**：可任选一条候选路径确认，或撤销已确认的绑定；其余明细随之
   重判。确认若导致整单无法配齐，则**拒绝该次确认并保留原绑定**，页面说明原因
   （原本就无法配齐时的确认可接受，并如实提示仍未配齐）。
5. **整单无法配齐**：页面逐条说明原因（无符合字段的有效路径 / 候选被确认绑定
   占用 / 候选与其他明细冲突）。
6. **并发保护**：每次绑定变更使状态版本 +1；旧页签持过期版本提交会被拒绝（409）
   并提示刷新。会话存于服务端文件（默认 `/tmp/backfill-jobs`，可用环境变量
   `BACKFILL_JOB_DIR` 覆盖），fcntl 排他锁保证多 worker / 多线程下读改写原子。
7. **下载**：仅当当前绑定下存在**唯一**完整配法时，才可下载补齐来源行号的 CSV
   （UTF-8 带 BOM，列与入仓明细一致，末两列已补齐）。
8. **上限**：每次最多核对 20 条明细、50 条有效路径（各明细候选的并集），
   超出即整次退回并提示。

### 唯一完整配法的判定

在“明细→路径”二部图上求饱和全部明细的匹配（匈牙利增广）。配法唯一当且仅当：
任何“候选但未匹配”的边指向的路径均已被占用（否则改配该明细即得另一套配法），
且交替有向图无环（否则沿环交换即得另一套配法）。两者均为 O(明细×路径) 级别，
不枚举全部配法。

## 错误处理（整次退回）

任一文件存在问题时，本次核对不产生任何部分结果，HTTP 400 进入错误页，
逐条列出**文件名 + CSV 物理行号 + 原因**，三个文件的错误一次性全部返回。
覆盖：表头不符、列数不符、日期格式、金额非整数/负数、必填为空、
单号或行号重复、有效期起日不早于止日、空文件、非 UTF-8、NUL 字节、缺传文件。

## 自测

```bash
python3 -I tests/test_reconcile.py     # 核对引擎 + 核对网页（需先 pip install Flask）
python3 tests/test_backfill.py         # 补录引擎 + 补录网页
```

脚本与数据目录分离并以 `-I` 隔离模式运行，避免从数据目录加载同名模块。

### 实测结果（本机，Python 3.11 + Flask 3.0.3）

- 核对套件 58 条断言、补录套件 58 条断言全部通过。补录套件覆盖：
  - 明细解析校验：表头、入仓行号唯一、同一单号、行号整数、必填非空、
    20 条明细上限、50 条有效路径上限、单号须在拨款表存在；
  - 候选路径按拨款日 + 已有字段过滤；状态分类（确认 / 唯一推定 / 待核 / 无候选）；
  - 一对一约束、确认导致整单无解被拒绝且保留原绑定、原本无解时确认可接受；
  - 撤销后恢复多解；唯一性判定覆盖交替环与交替路（候选集互不相交）两种多解情形；
  - Flask 端到端：上传建会话、确认、撤销、旧版本提交 409、唯一配法下载、
    多解 / 无解禁止下载、未知会话 404。
- 另用 gunicorn（2 worker × 4 线程）实起服务、curl 真实走查：
  - 样例四表上传 → 多解（2 待核）；确认 E1→(601,901) 后仍多解；
    旧版本提交返回 409“绑定已变化，请刷新”；确认 E2→(601,903) 后唯一，
    下载 CSV 补齐为 `E1→601,901`、`E2→601,903`；
  - 陷阱场景（X1 自由、X2 限定归属行号 601）：确认 X1→(601,901) 被拒，
    页面提示“该确认将导致整单无法配齐，已保留原绑定”，版本与绑定未变；
    改确认 X1→(602,901) 被接受并唯一配齐，下载 `X1→602,901`、`X2→601,901`；
  - 撤销 E2 确认后恢复多解、下载入口消失；
  - 无法配齐时页面列出原因（如“入仓行号 Y2：按拨款日没有符合已有字段的有效路径”）；
  - 21 条明细上传返回 400 并提示超上限；原核对入口 `/check` 回归正常。

## 未完成项 / 已知限制

1. 交付环境没有 Docker daemon，`docker compose up` 未在本机实跑；
   已通过 compose YAML 语法校验，并用同版本 gunicorn 做了等价的本地实跑验证。
2. 补录会话存于容器本地文件（默认 `/tmp/backfill-jobs`，保留 6 小时），
   容器重建后会话丢失，需重新上传；未做多实例共享存储（如 Redis）。
3. 结果仅当次展示与下载，未做持久化、历史记录或操作审计。
4. 文件全量读入内存，上传上限 16MB；未实现流式解析。
5. 有效期匹配为按项目/学院线性扫描；若单项目归属行或单学院归口行极多，
   可进一步改为按日期排序 + 二分查找（区间树）。
6. 金额只接受整数分，不接受浮点“元”；无登录鉴权与多用户隔离
   （任何知道会话链接的人都可查看 / 操作该会话）。
7. 自测为独立断言脚本，未引入 pytest，前端无浏览器自动化测试。
